# Flusso logico delle classi in funzionamento ordinario

Descrive l'ordine reale di esecuzione delle classi della pipeline PPRL (`primat-mqtt-common`, `primat-data-owner-service`, `primat-linkage-unit-service`) in un run senza errori, per capire "chi chiama chi" senza dover rileggere il codice.

## A. Lato Data Owner (un processo per party)

1. `DataOwnerService.main(args)` — legge `<configJsonPath>` (unico argomento), `DataOwnerConfigLoader.load(...)` legge e valida il JSON producendo `DataOwnerConfig` (party, sorgente dati, schema colonne, tuning RBF, `mqttBrokerUrl`; fissa anche `mqttClientId = "data-owner-" + party`); un JSON non valido termina il processo con un messaggio d'errore leggibile (`DataOwnerConfigException`), senza stack trace grezzo.
2. `DataOwnerService.start()`:
   - `MqttClientWrapper.connect()` — si connette al broker; se non è ancora raggiungibile, **ritenta all'infinito** ogni 2s (nessun limite di tentativi: il broker è un processo indipendente, `EmbeddedBrokerLauncher.main`, e i Data Owner possono partire anche prima di lui).
   - `client.subscribe(MqttTopics.commandTopic(party), handler)` — si mette in ascolto su `primat/do/{party}/cmd`.
3. `DataOwnerService.awaitForever()` — blocca il thread principale; la gestione dei messaggi in arrivo avviene sul thread di rete di Paho.
4. **Alla ricezione di uno `StartCommand`** (deserializzato da Gson **sul thread di callback Paho**, `CommsCallback`) → il listener registrato in `start()` delega subito `handleStartCommand(command)` a `commandExecutor`, un `ExecutorService` single-thread dedicato (2026-09-22): la deserializzazione resta sul thread Paho (istantanea), ma l'intera pipeline + le due `publish()` finali girano su un worker separato, cosi' il thread di callback Paho ritorna immediatamente e resta libero di consegnare eventuali comandi successivi (es. ripubblicazioni dallo stesso `LinkageUnitOrchestrator.collectRbf`) invece di restare bloccato per tutta la durata dell'elaborazione — prima di questo fix un Data Owner con una pipeline lunga (CSV grande, missing-value handling attivo) poteva restare "in ascolto" ma non rispondere più a nessun comando, vedi `CLAUDE.md`. `handleStartCommand(command)`:
   1. `newRecordSource()` → `CsvRecordSource` se `dataSourceType == CSV`, `JdbcRecordSource` se `DB` (entrambi effettivamente letti; `UnsupportedDataSourceException` resta solo come guardia per valori enum futuri non gestiti — vedi bullet 2026-09-17 in `CLAUDE.md`)
   2. `new DataOwnerPipeline(source, config).run()`:
      - `source.readAll(buildSchema())` — `CsvRecordSource` legge il CSV, `JdbcRecordSource` esegue `SELECT * FROM tableName`; entrambi mappano sullo stesso schema posizionale dichiarato in `config.getColumns()` (indice/nome/ruolo per colonna, non più hardcoded NCVR)
      - `buildPreprocessor()` → `FieldNormalizer.preprocess(records)`, applicato per **posizione** alle sole colonne QID ordinate per indice CSV crescente (**non** ai numeri di colonna CSV — `Record.getQidAttribute(int)` indicizza per posizione, vedi nota in `CLAUDE.md`): colonne `dataType: TEXT` con `NormalizerChain(TrimNormalizer, UpperCaseNormalizer, AccentRemover, SpecialCharacterRemover, SubstringNormalizer(0,20))`; colonne `dataType: NUMERIC` con `NormalizerChain(TrimNormalizer, NonDigitRemover)` — scelta per colonna dichiarata nel JSON, non più hardcoded sulla posizione 3/YOB
      - `buildRbfDefinition()` — un'unica `BloomFilterDefinition` "RBF" (lunghezza da `config.getBloomFilterLength()`, default 1024 bit) che unisce un `BloomFilterExtractorDefinition` per ogni colonna QID configurata: un `ConstantWeightTrigramExtractor` dedicato per colonna (trigram extractor con padding attivo e carattere `"_"`, che con `constantWeightEncoding.enabled` normalizza il numero di trigrammi unici dentro una banda `[minTrigrams, maxTrigrams]` — hash-ranking deterministico se in eccesso, filler derivati dall'hash del valore se in difetto; `enabled=false`/assente è equivalente byte-per-byte al vecchio `TrigramExtractor` condiviso), salt e numero di hash per colonna presi dal JSON con default se omessi (vedi `ColumnConfig.DEFAULT_HASH_FUNCTIONS`/`getSaltOrDefault()`), hashing `RandomHashing(length, SECURE_RANDOM)`, hardening da `config.getHardener()` (`NoHardener` di default, oppure `XorFolder(foldCount)` se `bloomFilter.hardening.type: XOR_FOLD` nel JSON)
      - `BloomFilterEncoder.encode(records)` → un `Record` per input, ciascuno con un solo `BitSetAttribute` RBF (i dati in chiaro non escono mai da questo passo). Se `missingValueHandling.enabled` nel JSON, un attributo QID vuoto (dopo normalizzazione) bypassa del tutto l'estrazione a q-gram: `BloomFilterEncoder.extractFeatures` chiama `MissingValueBucketing.generateTokens(record, anchorPriority, tokenCount)`, che sceglie un bucket (1 di 64, hardcoded) dall'hash del primo attributo QID non vuoto del record secondo `missingValueHandling.anchorPriority` (fallback su `Record.getId()` se tutti gli attributi sono vuoti) e genera token sintetici deterministici da quel bucket — invece dei trigrammi di padding fisso `"___"`, identici per ogni record con quell'attributo mancante nel comportamento pre-esistente
   3. Per ogni record codificato: `RbfCodec.toRbfRecord(record)` (Base64 di `BitSet.toByteArray()`) → raccolti in un `RbfPayload(runId, party, records)`
   4. `client.publish(MqttTopics.rbfTopic(runId, party), json)` — pubblica l'RBF sul topic `primat/lu/{runId}/rbf/{party}`
   5. `client.publish(MqttTopics.statusTopic(runId, party), StatusMessage("DONE"|"FAILED", ...))` — ack/errore, non letto dall'orchestratore in questa versione
5. Il Data Owner **torna in ascolto** sullo stesso topic di comando: un nuovo `StartCommand` (nuovo `runId`) riavvia il ciclo dal punto 4 senza riavviare il processo.

## B. Lato Linkage Unit (`LinkageUnitOrchestrator`)

1. `LinkageUnitOrchestrator.main(args)` — legge `<configJsonPath>` (unico argomento, dal 2026-09-16), `LinkageUnitConfigLoader.load(...)` legge e valida il JSON producendo `LinkageUnitConfig` (party attese, `clusteringMethod` — la sola fonte di verità su quale delle 6 strategie gira, niente più auto-routing dirty/clean — soglia di similarità, parametri LSH/MQTT/cluster/AP/MCL/Center Clustering/Global Greedy/CLIP, credenziali del DB dedicato se la strategia è persistente); un JSON non valido termina il processo con `Errore di configurazione: ...` (`LinkageUnitConfigException`), senza stack trace grezzo. Se il caricamento riesce, stampa subito `config.describe()` (2026-09-22, mirror di `DataOwnerConfig.describe()`) e poi istanzia l'orchestratore con quella config.
2. `LinkageUnitOrchestrator.start()`:
   - `client.connect(config.getBrokerConnectTimeoutSeconds())` — il client orchestratore si connette al broker esterno (`mqttBrokerUrl` top-level del JSON, già avviato a parte con `EmbeddedBrokerLauncher.main`, Moquette non persistente); se non è raggiungibile entro `mqtt.brokerConnectTimeoutSeconds` (default 30s) lancia `IllegalStateException`. Dal 2026-09-21 la LU non avvia più il broker.
3. `LinkageUnitOrchestrator.runOnce()` (un solo run per processo dal 2026-09-16; per un secondo run si rilancia il processo, eventualmente con un JSON diverso):
   1. `collectRbf(runId)`:
      - sottoscrive `MqttTopics.rbfTopicWildcard(runId)` (`primat/lu/{runId}/rbf/+`)
      - pubblica `StartCommand(runId, timestamp)` su `primat/do/{party}/cmd` per ogni party non ancora arrivato, **ripetendo ogni 3s** finché tutti gli RBF attesi arrivano o scade il timeout di 30s (mitiga la race in cui un Data Owner sottoscrive il comando dopo la prima pubblicazione)
      - alla ricezione di ogni RBF: `RbfCodec.toRecord(rbfRecord, party)` → accumulato in `Map<Party, Collection<Record>>` (il `input` "fresco" di questo run)
   2. **Blocking** — un solo blocker, `JaccardLshKeyGenerator` (MinHash, key size 4, 30 chiavi, range 1024, seed 42) dentro `LshBlocker`; `blocker.getBlocks(input)` viene invocato una volta solo per stampare il conteggio blocchi (`=== Blocking (JaccardLSH) - blocchi: N ===`), poi lo stesso `blocker` viene passato a `MultiSourceLinkage` per il run vero e proprio.
   3. **Persistenza vs CSV, decisa una volta sola (2026-09-17)** — prima dello switch, `runOnce()` calcola `persistenceEnabled = config.isPersistenceEnabled()`, `dbConnection = config.getDbConnection()` (costruito **lazy** al primo accesso — vedi `LinkageUnitConfig.getDbConnection()` — `null` se `!persistenceEnabled`) ed `effectiveInput = persistenceEnabled ? buildPersistentInput(input) : input`, poi li passa uniformemente a tutti e 5 i rami.
   4. **Dispatch a 5 vie da config JSON (2026-09-16, sostituisce il routing dirty/clean automatico del 2026-09-15; Global Greedy/CLIP aggiunti il 2026-09-17; MSCD_AP_NO_CLEAN rimosso il 2026-09-21)** — `runOnce()` fa uno switch su `config.getClusteringMethod()`. Una sola strategia gira per run: `MaxBothPostprocessor`/`GaleShapleyPostprocessor` (le vecchie SBM/SM) restano in libreria in `primat-linkage-unit`, semplicemente non più referenziate dalla pipeline.
      - **`CENTER_CLUSTERING`**: `MultiSourceLinkage.runCenterClustering(effectiveInput, blocker, config.getCenterClusteringConfig(), threshold, clusterFactory, dbConnection)` — se `dbConnection != null` persiste su `PrimatCenterClustering` (`PersistentLinkTableBuilder`), altrimenti resta in memoria (`LinkTableBuilder`).
      - **`MSCD_AP`**: `ApConfig` (da config) viene popolata dinamicamente (`parties.stream().filter(Party::isDuplicateFree)...forEach(apConfig::addCleanSource)`), poi `MultiSourceLinkage.runMscdAp(effectiveInput, blocker, apConfig, threshold, clusterFactory, dbConnection)` — DB dedicato `PrimatMscdAp` se `dbConnection != null`. Se nessuna party è `duplicateFree=true`, questo è già stato bloccato a monte da `LinkageUnitConfigLoader` (errore di caricamento config, non un fallback silenzioso).
      - **`MCL`**: `persistenceEnabled` è sempre `false` per MCL (`true` esplicito lancia `LinkageUnitConfigException` a caricamento config), quindi `dbConnection` è sempre `null` ed `effectiveInput == input` — `MultiSourceLinkage.runMcl(effectiveInput, blocker, config.getMclConfig(), threshold)` lavora solo sul batch fresco di questo run, nessuna interazione con Postgres per design.
      - **`GLOBAL_GREEDY`** (2026-09-17): richiede tutte le party `duplicateFree=true` (validato a monte da `LinkageUnitConfigLoader`). `MultiSourceLinkage.runGlobalGreedy(effectiveInput, blocker, config.getGlobalGreedyConfig(), threshold, clusterFactory, dbConnection)` — DB dedicato `PrimatGlobalGreedy` se `dbConnection != null`. Usa lo stesso motore condiviso di CLIP (`PriorityClusteringEngine`), parametrizzato con `EdgePriorityFunction.RAW_SIMILARITY` (ordina gli archi solo per similarità grezza).
      - **`CLIP`** (2026-09-17): stesso vincolo tutte-clean di Global Greedy. `MultiSourceLinkage.runClip(effectiveInput, blocker, config.getClipConfig(), threshold, clusterFactory, dbConnection)` — DB dedicato `PrimatClip` se `dbConnection != null`. Stesso `PriorityClusteringEngine`, ma con `ClipEdgePriorityFunction` (similarità + link-degree + classificazione STRONG/NORMAL/WEAK via `LinkStrength`, stesso criterio mutual-best-match di SBM).
      - **Dopo lo switch**: se `!persistenceEnabled`, `ClusterCsvWriter.write(outcome, config.getCsvOutputPath())` scrive la Link Table su CSV (per MCL è sempre il caso; per gli altri 4 solo se configurati con `persistence.enabled=false`).
   5. **Preparazione input persistente** — `buildPersistentInput(input)` (chiamata solo se `persistenceEnabled`, per qualunque metodo diverso da MCL), usa `dbConnection`:
      - `dbConnection.addParties(parties)` — registra sul DB dedicato alla strategia tutte le party attese per questo run (idempotente)
      - `dbConnection.getCandidateClusters(freshRecords)` — interroga il DB dedicato per i **soli** `Cluster` storici candidati, cioè quelli che condividono almeno una blocking key con un record fresco: `addBlockingKeysStaging(freshRecords)` popola la tabella temporanea `BlockStaging` (le chiavi LSH sui record freschi sono già state calcolate da `blocker.getBlocks(input)` al passo precedente), poi un join nativo `clusterBlock ↔ BlockStaging` seleziona gli id dei cluster candidati e una JPQL con fetch join carica i `Cluster` completi (record, attributi, blocking keys). Se non ci sono record freschi, ritorna subito un set vuoto senza interrogare. Il costo dipende dal numero di candidati, **non** dalla dimensione totale del DB — sostituisce il precedente `getAllRecordsWithClusters()` (reload completo dello storico), che resta nel codice solo per debug/verifica manuale
      - dedup per `Record.getId()`: un record fresco il cui id è già tra i candidati viene scartato a favore dell'oggetto persistito (che porta con sé il cluster); i record freschi rimanenti (mai visti) vengono uniti ai candidati in un unico `Map<Party, Collection<Record>>`
      - **Bug scoperto nel codice framework non toccato**: `Cluster.addRecord(Record)` popola `cluster.blockingKeys` (che sostiene `clusterBlock`) solo quando il record passato era **già** presente nell'insieme — nel flusso normale di aggiunta di un record nuovo e distinto questo non scatta mai, quindi `clusterBlock` non sarebbe mai popolata da nessun path esistente. `DbConnection` lo compensa esplicitamente con `syncClusterBlockingKeys(cluster)` (metodo privato, ricalcola l'unione delle blocking key di tutti i record del cluster), chiamato dentro `persistNewCluster`/`extendCluster`/`mergeClusters` subito prima del `persist`/`merge` finale. Conseguenza: i cluster persistiti **prima** di questa modifica hanno `blockingKeys` vuoto e non verranno trovati come candidati finché non esiste un fallback — verificare su un DB pulito (vedi `TESTING.md`)
   6. **Blocking + classificazione + clustering sul grafo N-ario unico**, condiviso da tutte le 5 `runXxx(...)` tramite il metodo privato `MultiSourceLinkage.classifyAndCluster(...)`:
        a. `classify(input, blocker, threshold)`:
           - `LshBlocker.getBlocks()` genera le coppie candidate
           - per ogni coppia candidata in blocco: `BitSetAttributeSimilarityCalculator` con `BinarySimilarity.JACCARD_SIMILARITY` calcola la similarità Jaccard tra i due bitset RBF
           - `ThresholdClassificator(threshold=0.6, aggregator)` decide match/non-match sulla base di quella similarità
           - `BatchMatcher.match()` produce un `LinkageResult` partizionato per `PartyPair` (A-B, A-C, B-C), **senza** ancora postprocessing 1:1 (`NoPostprocessor` su tutti i `LinkageConstraint`)
        b. `MultiPartiteSimilarityGraph.from(linkageResult)` fonde tutte le `PartyPair` in **un unico grafo N-ario** (nodi = `Record`, archi = `SimilarityVector` con similarità aggregata)
        c. `clusterer.cluster(graph)` (`MultipartiteClusteringStrategy`, implementata da `AffinityPropagationPostprocessor`/`MarkovClusteringPostprocessor`/`CenterClusteringPostprocessor`/`GlobalGreedyClusteringPostprocessor`/`ClipClusteringPostprocessor`) elabora **ogni componente connessa** del grafo (`graph.getConnectedComponentsSimGraph()`) come un unico problema di clustering multi-sorgente, non più per-`PartyPair`:
           - **MSCD-AP**: costruisce la matrice di similarità della componente e gli indici degli elementi delle sorgenti clean (`ApConfig.getCleanSources()`), poi `SparseMscdAffinityPropagationSeq.fit()` (motore invariato) — il vincolo clean-source ora vede l'**intera** componente connessa, non più una singola `PartyPair` alla volta: due record della stessa sorgente clean collegati solo transitivamente attraverso una terza party dirty vengono correttamente tenuti separati (test di regressione: `AffinityPropagationCleanSourceConstraintTest`)
           - **MCL**: costruisce la matrice di similarità **simmetrica** della componente (`simMatrix[i][j] = simMatrix[j][i]`, a differenza di MSCD-AP che scrive solo `[i][j]`, perché la normalizzazione per colonna di Markov Clustering richiede un grafo non orientato correttamente rappresentato), poi `MarkovClusteringEngine.fit()` (`addSelfLoops` → `columnNormalize` → iterazione `expand`/`inflate`/`prune` fino a convergenza o `maxIterations`, poi `extractClusters` via `MatrixUtils.argMax` sull'asse colonna); fast-path immediato per componenti ≤2 nodi; nessuna eccezione di non-convergenza (log di warning, si usa l'ultima matrice disponibile)
           - **Center Clustering** (2026-09-16): costruisce la stessa matrice simmetrica di MCL, ma con `vertexSet()` ordinato per chiave stabile `party#id` prima di assegnare gli indici (jgrapht non garantisce un ordine di iterazione stabile tra run/JVM, necessario per riprodurre lo stesso clustering — e quindi gli stessi `Cluster.id` — su run successivi), poi `CenterClusteringEngine.fit()`: **una sola passata greedy**, nessuna iterazione/convergenza (a differenza di MCL) — ordina gli archi per similarità decrescente e poi `(i,j)` ascendente, il primo arco libero su entrambi gli estremi crea un nuovo centro, un arco con un estremo già centro e l'altro libero assegna la foglia, ogni altro arco è scartato. Produce cluster "a stella" (centro + foglie dirette), **non** la chiusura transitiva del grafo — due foglie dello stesso centro non sono a loro volta collegate da un arco, e un nodo raggiungibile solo transitivamente resta un centro singoletto a sé
           - **Global Greedy / CLIP** (2026-09-17): stessa costruzione di matrice/`partyIds` di Center Clustering (stesso `stableKey` `party#id`), ma delegano a `PriorityClusteringEngine.fit()` (package condiviso `postprocessing/priority_clustering`): precalcola `rowMax[]`/`vertexDegree[]` una sola volta, ordina gli archi per la `EdgePriorityFunction` scelta (similarità grezza per Global Greedy, punteggio pesato similarità/link-degree/`LinkStrength` per CLIP — scartando a priori gli archi con priorità `NEGATIVE_INFINITY`, es. i link WEAK di CLIP quando `ignoreWeakLinks=true`) e poi unisce via union-find (path halving/union by rank), rifiutando ogni merge che farebbe convivere due record della stessa party nello stesso cluster (un `BitSet` per radice, controllo diretto **e** transitivo attraverso una terza party — a differenza di Center Clustering, che non impone questo vincolo)
           - tutte e 4 le strategie generano, per ogni gruppo di label/etichetta, tutte le coppie non ordinate (clique completa, `i<j`, non solo gli archi centro-foglia per Center Clustering) come `LinkedPair<Record>` — necessario per non raddoppiare artificialmente i conteggi TP/FP di `QualityEvaluator`/`countGroundTruthMatches` e per rispettare la convenzione di output richiesta da `PersistentLinkTableBuilder`/`LinkTableBuilder`
        d. chiusura finale sulla Link Table — **Center Clustering / MSCD-AP / Global Greedy / CLIP** scelgono tra due builder in base a `dbConnection` (`null` se `persistence.enabled=false`, vedi sopra):
           - **`dbConnection != null`**: `PersistentLinkTableBuilder.build(matches, allRecords, clusterFactory, dbConnection)` — seeda l'union-find unendo prima i record che appartengono già allo **stesso** cluster persistito (da run precedenti, un link già stabilito non può mai essere smontato silenziosamente da questo run), applica poi i `LinkedPair` di questo run e calcola le componenti connesse; per ognuna, conta quanti `Cluster` persistiti distinti sono referenziati dai suoi membri: **0** → `dbConnection.persistNewCluster(...)` (nuovo cluster); **1** → `dbConnection.extendCluster(...)` (estende quello esistente con i soli membri nuovi, no-op se non ce ne sono); **≥2** → `dbConnection.mergeClusters(target, losers, nuovi)` (target = id più basso; i cluster perdenti vengono svuotati e cancellati dopo aver ripuntato i loro record al target) — risultato: i `Cluster.id` sono **stabili tra run** (assegnati dal DB dedicato alla strategia, non da un contatore locale). Global Greedy/CLIP usano ciascuna il proprio `DbConnection` dedicato (`PrimatGlobalGreedy`/`PrimatClip`), mai quello di un'altra strategia (vedi `CLAUDE.md`, bullet 2026-09-17, sul perché nessuna PU va condivisa)
           - **`dbConnection == null`** (sempre il caso per MCL; per gli altri 4 quando configurati con `persistence.enabled=false`): `LinkTableBuilder.build(matches, allRecords)` — union-find in memoria (non `SimpleClusterBuilder`, che ha un difetto noto: ritorna sempre un set vuoto), id di cluster locali che ripartono da 0 ad ogni run, nessuna persistenza; se `persistence.enabled=false` la Link Table viene poi scritta su CSV da `ClusterCsvWriter` (vedi sopra)
        e. `QualityEvaluator` + `IdEqualityTrueMatchChecker` calcolano TP/FP; **solo sulle coppie cross-party** di `aggregatedMatches` (fix 2026-09-15: prima venivano contate anche le coppie within-party, es. due duplicati della stessa sorgente dirty ritrovati correttamente dal clustering, gonfiando la recall oltre 1 — vedi CLAUDE.md), filtrate in `buildOutcome` prima di `evaluator.addMatches(...)`; la `linkTable`/`matches` restituite in `LinkageOutcome` restano invece complete, non filtrate. `countGroundTruthMatches(input)` conta le coppie di ground truth attese (stesso `GLOBAL_ID` tra party diversi, sempre cross-party) — per MSCD-AP questo denominatore è calcolato sull'input persistente (storico+fresco), per MCL sul solo batch fresco; `QualityMetrics` calcola recall/precision/F-measure
      - risultato: `LinkageOutcome` (Link Table + metriche), stampato da `printOutcome()`/`printLinkTable()`

## Tabella riassuntiva: soglie e parametri

| Parametro | Valore | Dove | Effetto |
|---|---|---|---|
| JaccardLSH (MinHash) key size / numero chiavi | 4 bit / 30 chiavi | `LinkageUnitOrchestrator.runOnce` | soglia di banding effettiva s*≈0.39 (formula `s*=(1-0.5^(1/b))^(1/r)`, b=30, r=4); unico blocker usato, sia per la stampa diagnostica sia per il risultato finale di tutte e tre le strategie |
| LSH value range | 1024 | idem | = lunghezza del bitset RBF |
| LSH seed | 42 | idem | riproducibilità delle chiavi generate; ogni combinazione (banda, permutazione) usa un seed distinto (bug seed di `JaccardLshKeyGenerator` corretto) |
| Numero hash per attributo (Bloom Filter, lato encoding) | FN 12, MN 3, LN 13, YOB 13, BIRTH_PLACE 3, CITY 2 | campo `hashFunctions` per colonna in `primat-data-owner-service/src/main/resources/config/examples/example_{clean,dirty}/party_{A,B,C}_*.json` (FEBRL: `config/febrl/*/party_org*.json` con `given_name`/`surname`/`date_of_birth`=25, `suburb`/`postcode`=6, `state`=3)` (letto da `DataOwnerPipeline.buildRbfDefinition()` via `ColumnConfig`; stessi valori replicati in `DataSources.getEncodedNCVR`, non più hardcoded nel Data Owner Service dal 2026-09-16) | densità di bit attivi nell'RBF per attributo, ritarati per il blocking solo-JaccardLSH |
| Chiave hashing RBF | fissa, `"SECRET"` (`RandomHashing.DEFAULT_KEY`) | `RandomHashing.getRandom()` (chiamata da `buildRbfDefinition()`) | nonostante il nome, `RandomHashing` è **deterministica**: risemina il PRNG con l'HMAC-SHA384 del trigramma+chiave, quindi stesso testo → stesso bitset in ogni run. Necessario perché un'impronta fresca sia confrontabile per similarità con una storica salvata in un run precedente (persistenza MSCD-AP) — non va confuso con il riconoscimento "stesso record già visto", che si basa solo sull'uguaglianza di `Record.getId()`, non sul bitset |
| Preprocessing (Data Owner) | trigrammi (q=3), padding attivo, carattere `"_"` | `DataOwnerPipeline.buildRbfDefinition()` | 2 caratteri di padding per lato (q-1) prima dell'estrazione dei trigrammi |
| Constant Weight Encoding (per colonna, JSON `columns[].constantWeightEncoding`) | `enabled`/`minTrigrams`/`maxTrigrams`, opzionale, default disabilitata | `ConstantWeightTrigramExtractor` (primat-common), costruito da `DataOwnerPipeline.buildRbfDefinition()` | normalizza il numero di trigrammi unici per attributo dentro banda `[min,max]`: hash-ranking deterministico se in eccesso, filler da hash del valore se in difetto (mai su valore vuoto); mitiga attacchi a frequenza basati sulla lunghezza della stringa |
| Missing-value bucketing (JSON top-level `missingValueHandling`) | `enabled`/`anchorPriority` (lista nomi colonna QID), opzionale, default disabilitato; numero bucket fisso `MissingValueBucketing.NUM_BUCKETS=64` (non in JSON) | `BloomFilterEncoder.extractFeatures` → `MissingValueBucketing` (primat-data-owner) | un attributo vuoto non produce più lo stesso padding `"___"` per tutti i record: il bucket (e quindi i bit RBF) dipende dall'hash del primo attributo QID non vuoto secondo `anchorPriority`, riducendo la correlazione strutturale tra record diversi con lo stesso campo mancante |
| Soglia similarità Jaccard | **0.6** (default, override via JSON `similarityThreshold`) | `LinkageUnitConfig.getSimilarityThreshold()`, passata a `ThresholdClassificator` in `MultiSourceLinkage.classify()` | soglia di match/non-match sulla similarità Jaccard tra bitset RBF (dopo il blocking) |
| Timeout raccolta RBF | 30s (default, override via JSON `mqtt.rbfCollectionTimeoutSeconds`) | `LinkageUnitConfig.getRbfCollectionTimeoutSeconds()` | scadenza oltre la quale `collectRbf` fallisce |
| Intervallo repubblicazione comando | 3s (default, override via JSON `mqtt.rbfRepublishIntervalSeconds`) | `LinkageUnitConfig.getRbfRepublishIntervalSeconds()` | frequenza di ripubblicazione dello `StartCommand` ai party mancanti |
| Quale strategia gira | dichiarata dal JSON, campo `clusteringMethod` (2026-09-16, niente più default/auto-routing; Global Greedy/CLIP aggiunti il 2026-09-17; MSCD_AP_NO_CLEAN rimosso il 2026-09-21) | `LinkageUnitConfig.getClusteringMethod()` | `CENTER_CLUSTERING` / `MSCD_AP` / `MCL` / `GLOBAL_GREEDY` / `CLIP`, sola fonte di verità |
