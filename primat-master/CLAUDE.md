# PRIMAT: Private Matching Toolbox

Multi-module Maven project (groupId `de.uni-leipzig.dbs.pprl`, artifactId `primat`, version `1.0.3`, Java 11) implementing PPRL (Privacy-Preserving Record Linkage) workflows: Bloom-filter encoding/hardening, LSH-based blocking, similarity classification, and post-processing (clustering) for 1:1 and multi-source record linkage.

## Build & Run

No `mvn` on PATH in this environment; use the bundled IntelliJ Maven if needed:
`C:\Program Files\JetBrains\IntelliJ IDEA <version>\plugins\maven-plugin\lib\maven3\bin\mvn` with `JAVA_HOME` set to the IntelliJ-bundled JBR.

- Build everything: `mvn install -DskipTests` (root pom, reactor build)
- Build specific modules only: `mvn -pl <module1>,<module2> -am install -DskipTests`
- Run tests: `mvn test` (JUnit Jupiter 5.1.0)
- Run a single test class: `mvn -pl <module> test -Dtest=ClassName`
- Incremental matching **and** the persistent MSCD-AP path of `primat-linkage-unit-service` (`LinkageUnitOrchestrator` / `PersistentLinkTableBuilder`) require PostgreSQL: create a `primat` database and edit `primat-linkage-unit/src/main/resources/META-INF/persistence.xml` with your credentials.

## Module Index

- `primat-common` — shared data model (`Record`, `Party`, `Cluster`, QID/non-QID attribute types), utilities (`DatasetReader`, hashing, feature extraction, LSH key generators). See `primat-common/.../common/CLAUDE.md`.
- `primat-data-owner` — pre-processing (normalizers, `FieldNormalizer`) and encoding (Bloom filter encoding/hardening) run on the data owner side. See `primat-data-owner/.../dataowner/CLAUDE.md`.
- `primat-linkage-unit` — core linkage framework: blocking (standard + LSH), similarity calculation/classification, post-processing/clustering (`AffinityPropagationPostprocessor` and `MarkovClusteringPostprocessor`, both `MultipartiteClusteringStrategy`; `MaxBothPostprocessor`/`GaleShapleyPostprocessor` remain as unused library code, see below), quality evaluation. See `primat-linkage-unit/.../lu/CLAUDE.md`.
- `primat-examples` — example workflows (`DataSources` setup, `BatchMatching`) showing canonical construction chains for encoding and linkage. See `primat-examples/.../examples/CLAUDE.md`.
- `primat-analysis` — tools for analyzing records and error types. See `primat-analysis/.../analysis/CLAUDE.md`.
- `primat-mqtt-common` — MQTT pub/sub plumbing (Paho client, Moquette broker launchable as a standalone process via `EmbeddedBrokerLauncher.main` / `mvn -pl primat-mqtt-common exec:java -Dexec.args="1883"`, Gson DTOs, `RbfCodec`) shared by the two service modules below. The broker must be started first, see `TESTING.md` section 2bis.
- `primat-data-owner-service` — long-running Data Owner process, entirely configured from a single JSON file passed as the only CLI arg (`DataOwnerConfigLoader`, package `.../service/config/`, see the 2026-09-16 bullet below): reads local CSV or a JDBC DB table (`RecordSource`: `CsvRecordSource`/`JdbcRecordSource`, both fully implemented — see the 2026-09-17 bullet below), preprocesses each QID column with the text chain (trim/uppercase/accent-removal/special-char-removal/truncation-to-20-chars) or the numeric chain (trim/digit-only) based on its configured `dataType`, encodes into a single Record-level Bloom Filter (RBF) per record using trigram features with `"_"` padding (length, per-column hash count/salt, and hardening — `NoHardener` or `XorFolder` XOR-folding — all from JSON), publishes only the RBF over MQTT (never plaintext).
- `primat-linkage-unit-service` — long-running Linkage Unit orchestrator: connects to the external MQTT broker (`mqttBrokerUrl` top-level JSON field, fails after `mqtt.brokerConnectTimeoutSeconds` if unreachable), commands Data Owners, collects RBFs, runs JaccardLSH blocking and produces a multi-source Link Table via `MultiSourceLinkage`, routing each run to exactly one of 5 clustering strategies declared by a JSON config file (see the 2026-09-16 bullet below, which supersedes the dirty/clean auto-routing described in the 2026-09-15 bullets further down, the 2026-09-17 bullet which adds Global Greedy/CLIP, and the 2026-09-21 bullet which removes MSCD_AP_NO_CLEAN). Persistence to a dedicated Postgres per strategy (via `PersistentLinkTableBuilder`) vs. generic CSV export is now a per-run JSON choice (`persistence.enabled`, default `true` except for MCL which can never persist) — see the 2026-09-17 bullet below.

## Architecture Notes (cross-cutting, not obvious from any single file)

- **Data Owner Service is now JSON-configured, CLI takes only the config path (2026-09-16)** — `DataOwnerService.main(args)` used to take 3 positional args (`<party> <csvFilePath> <brokerUrl>`) with the CSV schema/normalizer chains/RBF tuning hardcoded for the NCVR dataset (`DataOwnerConfig`/`DataOwnerPipeline`). Now it takes a single argument, the path to a JSON config file, loaded and validated by `DataOwnerConfigLoader` (`primat-data-owner-service/.../service/config/`) into the new, richer `DataOwnerConfig`. The JSON declares: `party`, `mqttBrokerUrl`; `dataSource` (`type: CSV` with `csv.filePath`, or `type: DB` with `db.tableName`/`jdbcUrl`/`username`/`password` — validated but **not implemented**, `DataOwnerService.newRecordSource()` throws `UnsupportedDataSourceException` if actually used, per explicit request to leave the extension point open without writing JDBC code); `columns` (one entry per CSV column: `index`, `name`, `role` — `PARTY`/`GLOBAL_ID`/`ID`/`QID`, exactly one `PARTY` and one `ID` required, at most one `GLOBAL_ID`, at least one `QID` — and for `QID` columns a `dataType` of `TEXT` or `NUMERIC` that selects which hardcoded `NormalizerChain` `DataOwnerPipeline.buildChainFor` builds, plus optional per-column `hashFunctions`/`salt` for the RBF extractor, defaulting to `ColumnConfig.DEFAULT_HASH_FUNCTIONS`/`name + "_"` if omitted); optional `bloomFilter` (`length`, default 1024, and `hardening` — `NONE` or `XOR_FOLD` with a required `foldCount`, mapping to the pre-existing `NoHardener`/`XorFolder` classes in `primat-data-owner`'s hardening package — **no new hardening algorithm was written**, `XorFolder` already implemented XOR-folding [Schnell, Borgs 2016], it just wasn't wired into this pipeline before). `DataOwnerPipeline.buildSchema/buildPreprocessor/buildRbfDefinition` went from hardcoded-NCVR `private static` methods to instance methods iterating `config.getColumns()`; QID columns are sorted by CSV index ascending before assigning `FieldNormalizer` positions 0..n-1 (still driven by list position per the `Record.getQidAttribute(int)` note below, now generalized instead of hardcoded to 6 fixed NCVR columns). The QID attribute type in the schema stays `QidAttributeType.STRING` regardless of `dataType` — `dataType` only picks the normalizer chain, deliberately not the underlying `Attribute` class, to avoid changing the already-validated trigram-based RBF extraction. All config-loading/validation errors surface as a single checked `DataOwnerConfigException` (file missing/unreadable, malformed JSON, missing/invalid fields, duplicate column index/name, missing required roles, QID column missing `dataType`, non-positive `hashFunctions`/`bloomFilter.length`, `foldCount` incompatible with `bloomFilter.length`); `DataOwnerService.main` catches it and exits with a readable message instead of a raw stack trace. Example JSON configs live in `primat-data-owner-service/src/main/resources/config/{examples,febrl}/` (NCVR `party_{A,B,C}_{clean,dirty}.json` and `examples/example_db.json` under `examples/`; FEBRL `party_org*.json` under `febrl/<scenario>/`); `DataOwnerConfigLoaderTest` (new — this module had zero tests before) covers the happy path and one case per validation failure.
- **ID record univoci tra sorgenti (2026-09-21)** — `DataOwnerPipeline.run()` (`prefixRecordIds`) prepone il `party` del JSON (non la colonna CSV `PARTY`) all'ID locale di ogni record subito dopo la lettura (`party + id`, nessun separatore: `A` + `1` → `A1`), perché la LU deduplica/persiste per `Record.getId()` e gli ID devono essere unici cross-party. I CSV in `primat-examples/.../synthetic_ncvr/` ora hanno ID nudi (`1`, `2`, ...); coperto da `DataOwnerPipelineIdPrefixTest`.
- **CSV con header opzionale (2026-09-21)** — `dataSource.csv.hasHeader` (boolean, default `false`) nel JSON del Data Owner: se `true` la prima riga del CSV viene saltata (`CsvRecordSource(filePath, hasHeader)` → `DatasetReader(filePath, hasHeader, schema)`); prima l'header veniva letto come record spurio. Coperto da `DataOwnerPipelineIdPrefixTest.hasHeaderSkipsFirstRow`.
- **RBF encoding**: a Record-level Bloom Filter is just a single `BloomFilterDefinition` whose `featureExtractors` list covers every QID attribute (see `DataSources.getEncodedNCVR` in `primat-examples`, replicated in `DataOwnerPipeline`) — no dedicated "RBF" class exists in the framework.
- **`Record.getQidAttribute(int column)` indexes by position** in the record's internal QID-attribute list (as added via schema config), **not** by original CSV column number. Any new `Preprocessor`/`NormalizeDefinition` must use list positions (0..n-1), not source column indices — a pre-existing `// TODO: ID Column problem` in `Record.java` documents this.
- **SBM/SM/MSCD-AP terminology**: these are literature names for post-processing/1:1-matching strategies, not class names in the codebase. Map them to `MaxBothPostprocessor` (Symmetric Best Match), `GaleShapleyPostprocessor` (Stable Marriage), `AffinityPropagationPostprocessor` (multi-source clean/dirty affinity propagation). **As of 2026-09-15, SBM and SM are no longer part of the pipeline** — see below.
- SBM and SM operate on a 2-party similarity graph (one `PartyPair`) and produce pairwise 1:1 links — extending to an N-source Link Table requires a separate transitive-closure cluster-building step over the `LinkedPair`s. MSCD-AP and MCL instead cluster directly on a single multi-party graph (`MultiPartiteSimilarityGraph`) in one step, per connected component.
- **Clean/dirty routing replaces the fixed 3-strategy pipeline, MCL introduced (2026-09-15)** — **il routing dirty/clean automatico descritto qui è superato dal bullet 2026-09-16 sopra** (la strategia è oggi dichiarata dalla config JSON, `chooseStrategy` è diventato `anyPartyDuplicateFree` e serve solo da validazione). Il resto di questo bullet (introduzione di MCL, `MultipartiteClusteringStrategy`, rimozione di SBM/SM dalla pipeline) resta valido: `LinkageUnitOrchestrator.runOnce()` non esegue più SBM/SM/MSCD-AP in sequenza. `MaxBothPostprocessor`/`GaleShapleyPostprocessor` (SBM/SM) and their tests are untouched and remain in `primat-linkage-unit` as generic library code, simply no longer referenced by the pipeline; `PostprocessingUnavailableException` was removed as dead code (MCL never throws a non-convergence exception by design). Both strategies now implement a shared `MultipartiteClusteringStrategy.cluster(MultiPartiteSimilarityGraph)` interface (new, sibling of `Postprocessor`) instead of running per-`PartyPair`: `AffinityPropagationPostprocessor` implements both `Postprocessor<T>` (existing `clean()`, untouched, still used by `primat-examples`) and `MultipartiteClusteringStrategy` (new `cluster()` method, operating on the whole connected component at once — this closes a real gap where the old per-`PartyPair` architecture could never detect two records of the *same* clean source connected only transitively through a third dirty party, letting `LinkTableBuilder`'s global transitive closure merge them incorrectly; regression-tested by `AffinityPropagationCleanSourceConstraintTest` in `primat-linkage-unit-service`). New package `primat-linkage-unit/.../lu/postprocessing/markov_clustering/` (`MarkovClusteringEngine` — pure engine, no `Record`/`Party`/graph dependency, `addSelfLoops`→`columnNormalize`→iterative `expand`/`inflate`/`prune` until convergence or `maxIterations`, fast-path for components ≤2 nodes, never throws on non-convergence; `MarkovClusteringPostprocessor` — wiring on `MultiPartiteSimilarityGraph`, symmetric similarity matrix per connected component; `data_structures/MclConfig` — `expansionPower=2`, `inflationExponent=2.0`, `pruningThreshold=1e-4`, `maxIterations=100`, `convergenceEpsilon=1e-6`, `selfLoopWeight=1.0`). MCL is **not persistent** (unlike MSCD-AP): every run recomputes from scratch, no stable `Cluster.id` across runs, zero interaction with `DbConnection`/Postgres. `MultiSourceLinkage.run`/`runPersistent` (parametrized by `LinkStrategy`) were replaced by `runMscdAp`/`runMcl` (each hardcoding its own clustering strategy); `LinkStrategy` enum is now just `{ MSCD_AP, MCL }` (result tag, no longer a dispatch parameter).
- **MCL debug export (2026-09-15, gate ora in config JSON — vedi bullet 2026-09-16 sopra)** — when the run routes to MCL, `LinkageUnitOrchestrator.writeMclDebugFile(outcome, outputPath)` overwrites the configured CSV path (default `mcl_debug_output.csv`; CSV: `cluster_id,party,record_id,global_id`) in the working directory, for later offline evaluation without repeating the run. Gated by `config.isMclDebugExportEnabled()` (JSON `mcl.debugExport.enabled`, default `true` — was the hardcoded constant `LinkageUnitOrchestrator.MCL_DEBUG_EXPORT` before 2026-09-16); no effect on the persistent branches, evaluated directly from their own Postgres. See `TESTING.md` for the Python evaluation scripts (`evaluate_mcl.py` reads this CSV, `evaluate_mscd_ap.py`/`evaluate_all.py` connect to Postgres).
- **`GaleShapleyPostprocessor` fixed (2026-09-14)** — previously had two stacked bugs, both now fixed in `primat-linkage-unit/.../postprocessing/stable_marriage/GaleShapleyPostprocessor.java`:
  - `clean()` called `SimilarityGraph.getGraph().removeAllEdges(...)`, but `getGraph()` always returns an unmodifiable `AsUnmodifiableGraph` wrapper → `UnsupportedOperationException` for any input, making SM always unavailable. Fixed by using `graph.retainAllEdges(marriedWoman.values())` (the mutable method already used by `MaxBothPostprocessor`).
  - Masked by the bug above and only surfaced once it was fixed: the divorce branch of the proposal loop was missing a `break`, so a man who won a woman by divorcing a rival kept proposing to his remaining preferences in the same turn, ending up "married" to multiple women while the divorced man could end up unmatched — an invalid, non-stable outcome. Fixed by adding `break` after the divorce/remarry in `GaleShapleyPostprocessor.java`.
  - Covered by `GaleShapleyPostprocessorTest` (new), which exercises the divorce path and asserts a proper stable 1:1 matching.
- **`JaccardLshKeyGenerator` fixed (2026-09-14)** — `generate()` (`primat-common/.../extraction/lsh/JaccardLshKeyGenerator.java`) previously computed each permutation's seed from `this.keySize`/`this.keys` instead of the loop variables, so every permutation across all keys/keySize was identical and JaccardLSH blocking degenerated. Fixed by using the loop variables (which now correctly shadow the same-named fields) in the seed formula. Covered by `JaccardLshKeyGeneratorTest` (new, in `primat-common`), asserting permutations differ both across `keySize` within one key and across different keys.
- **Only JaccardLSH blocking (2026-09-15)** — `LinkageUnitOrchestrator` no longer runs the HammingLSH-vs-JaccardLSH comparison (`BlockingComparison` deleted); it blocks solely with `JaccardLshKeyGenerator(keySize=4, keys=30, valueRange=1024, seed=42L)`. Per-attribute Bloom Filter hash counts were retuned accordingly in `DataOwnerPipeline`/`DataSources.getEncodedNCVR`: FN 25→12, MN 5→3, LN 15→13, YOB 30→13, BIRTH_PLACE 5→3, CITY 5→2.
- **Persistenza Link Table MSCD-AP (2026-09-15, `DbConnection` da allora diventata classe non più enum — vedi bullet 2026-09-16 sopra)** — `primat-linkage-unit-service` ha un path che rende stabili tra run i `Cluster.id` delle strategie persistenti (MCL, l'unica strategia non persistente, resta non persistita per design — vedi sopra):
  - `MultiSourceLinkage.runMscdAp(...)` usa `PersistentLinkTableBuilder` (classe dedicata) al posto di `LinkTableBuilder` (usato invece da `runMcl(...)`) per il passo finale di chiusura transitiva.
  - `PersistentLinkTableBuilder.build(...)` seeda l'union-find con l'appartenenza ai `Cluster` già persistiti (`Record.getCluster()`) prima di applicare i `LinkedPair` del run corrente — i cluster possono quindi solo fondersi tra run, mai dividersi — poi riconcilia ogni componente connessa con lo storico su DB: nessun cluster persistito referenziato → nuovo cluster; uno solo → lo estende; due o più → li fonde (target = id più basso, gli altri vengono eliminati dopo aver ripuntato i loro record).
  - `DbConnection` ha 4 metodi additivi (nessuna modifica ai metodi esistenti): `getAllRecordsWithClusters()`, `persistNewCluster(...)`, `extendCluster(...)`, `mergeClusters(...)`.
  - `LinkageUnitOrchestrator.runOnce()`, solo nel ramo MSCD-AP, interroga i cluster storici candidati (`buildPersistentInput`, vedi sotto) e li unisce (dedup per `Record.getId()`) al batch fresco prima di chiamare `runMscdAp(...)`. Da quando esiste il routing clean/dirty (vedi sopra) non c'è più un problema di ordine tra strategie: una sola strategia gira per run, quindi non può più verificarsi il precedente crash da `Record.getCluster()` corrotto da cluster transitori di un'altra strategia in-memory.
- **Blocking mirato sui cluster candidati per la persistenza MSCD-AP (2026-09-15)** — `LinkageUnitOrchestrator.buildPersistentInput` non ricarica più `getAllRecordsWithClusters()` (l'intero storico persistito) ad ogni run: usa invece `DbConnection.getCandidateClusters(freshRecords)`, che popola la tabella temporanea `BlockStaging` con le blocking key dei soli record freschi (`addBlockingKeysStaging`, corretto per essere richiamabile più volte nello stesso processo con un `DROP TABLE IF EXISTS` prima della `CREATE TEMPORARY TABLE`) e fa un join nativo `clusterBlock ↔ BlockStaging` per trovare i cluster storici candidati, poi li carica completi via JPQL con fetch join. Il costo dipende dal numero di candidati, non dalla dimensione totale del DB. `getAllRecordsWithClusters()` resta nel codice, non più usata dal path MSCD-AP, solo per debug/verifica manuale.
  - **Bug scoperto in `Cluster.addRecord(Record)` (codice framework non toccato, `primat-common/.../model/Cluster.java`)**: popola `cluster.blockingKeys` (che sostiene `clusterBlock`) solo quando il record passato era **già** presente nell'insieme (`this.records.add(rec)` ritorna `false`) — nel flusso normale di aggiunta di un record nuovo e distinto questa condizione non si verifica mai, quindi `clusterBlock` non sarebbe mai popolata da nessun path esistente. Workaround in `DbConnection`: nuovo metodo privato `syncClusterBlockingKeys(cluster)` ricalcola esplicitamente l'unione delle blocking key di tutti i record del cluster, chiamato subito prima del `persist`/`merge` finale in `persistNewCluster`/`extendCluster`/`mergeClusters`.
  - **Limite noto, non "risolto" in questo passaggio**: i cluster già persistiti prima di questa modifica hanno `clusterBlock` vuota e non emergeranno mai come candidati (nessun fallback previsto) → un record nuovo che appartiene a un'entità già nota ma pre-esistente creerebbe un cluster duplicato invece di estendere quello giusto. Per questo la verifica end-to-end va rifatta su un DB pulito (`DROP SCHEMA public CASCADE; CREATE SCHEMA public;`), vedi `TESTING.md`.
- **La codifica RBF è deterministica, non casuale**, nonostante il nome `RandomHashing`/`RandomFactory.SECURE_RANDOM`: `RandomHashing.getRandom()` risemina il PRNG con l'HMAC-SHA384 del trigramma + una chiave fissa (`RandomHashing.DEFAULT_KEY = "SECRET"`), quindi stesso testo in chiaro → stesso bitset, sempre, in ogni run/processo. È condizione necessaria per la persistenza MSCD-AP: un'impronta fresca di questo run è confrontabile via similarità con un'impronta storica salvata in un run precedente solo perché entrambe usano la stessa mappatura deterministica. Il riconoscimento "stesso record fisico già visto" (dedup in `buildPersistentInput`) è invece un meccanismo del tutto separato, basato sull'uguaglianza di `Record.getId()` (id locale in chiaro, non sul bitset).
- **SQL logging spento di default (2026-09-15)** — `persistence.xml` aveva `hibernate.show_sql`/`hibernate.format_sql` hardcoded a `true` (nessuna config di logging nel progetto: niente logback/log4j/SLF4J, Hibernate stampa direttamente su `System.out`), quindi ogni run che tocca `DbConnection` (oggi le 3 strategie persistenti — vedi bullet 2026-09-16 sopra, `DbConnection` non è più un enum con un'unica PU `"Primat"` hardcoded) stampava ogni statement SQL formattato su stdout. `persistence.xml` ora ha questi due valori a `false` come default committato in ciascuna delle 3 persistence-unit; il valore reale è però `DbConnection.SQL_DEBUG_LOGGING` (costante privata, `false`), che sovrascrive le due proprietà nella `Map` passata a `Persistence.createEntityManagerFactory(persistenceUnitName, overrides)` a runtime. Riattivare il logging SQL per debug flippando quella costante, non modificando `persistence.xml`.
- **Config JSON per la Linkage Unit + Center Clustering + persistenza multi-DB (2026-09-16)** — sostituisce l'auto-routing dirty/clean e i 2 rami MSCD-AP/MCL descritti nei bullet 2026-09-15 sottostanti (parzialmente obsoleti, tenuti per la storia dei fix che restano validi — es. il fix `recall > 1`, il blocking mirato sui candidati). Novità:
  - **`ClusteringMethod` a 4 valori** (`CENTER_CLUSTERING`, `MSCD_AP`, `MSCD_AP_NO_CLEAN`, `MCL`), letto da un nuovo file JSON (mirror esatto del pattern Data Owner: `LinkageUnitConfigLoader`/`LinkageUnitConfig`/Gson, package `primat-linkage-unit-service/.../lu/service/config/`) — **sola fonte di verità** su quale strategia gira, niente più auto-routing basato su `Party.isDuplicateFree()`. `LinkageUnitOrchestrator(List<Party>)`/`setParties(...)` sono spariti: il costruttore prende un `LinkageUnitConfig`, `main(String[] args)` prende un solo argomento (path del JSON), un solo run per processo (multi-run con party diverse = due file JSON + due processi).
  - **`chooseStrategy` rinominato `anyPartyDuplicateFree`** (`static boolean`, non più `LinkStrategy`): usato solo come regola di validazione dentro `LinkageUnitConfigLoader` (MSCD_AP senza nessuna party `duplicateFree=true` è un errore di caricamento, non un fallback silenzioso a MSCD_AP_NO_CLEAN).
  - **Center Clustering** (nuovo, `primat-linkage-unit/.../lu/postprocessing/center_clustering/`): `CenterClusteringEngine` (motore puro `double[][]→int[]`, greedy a singola passata, **non transitivo** — produce cluster "a stella" centro+foglie, non la chiusura transitiva del grafo, testato esplicitamente con una catena 0-1-2 senza arco 0-2), `CenterClusteringPostprocessor` (wiring su `MultiPartiteSimilarityGraph`, stesso pattern di `MarkovClusteringPostprocessor` ma con `vertexSet()` ordinato per chiave stabile `party#id` prima di assegnare gli indici, perché jgrapht non garantisce un ordine di iterazione stabile e l'algoritmo deve essere riproducibile per la persistenza), `data_structures/CenterClusteringConfig`. Deterministico e "leggero" (nessuna iterazione/convergenza), per questo — a differenza di MCL — si presta alla persistenza.
  - **MSCD-AP-no-clean**: nessuna classe nuova, è `MultiSourceLinkage.runMscdAp(...)` riusato tale e quale — la differenza è solo che `LinkageUnitOrchestrator` non popola `ApConfig.cleanSources` in questo ramo, degradando AP a comportamento tradizionale (utile per testare AP anche su scenari tutte-dirty).
  - **`DbConnection` da enum a classe** (`primat-linkage-unit/.../lu/database/DbConnection.java`): niente più singleton `DbConnection.INSTACE` (typo storico, rimosso in questo passaggio insieme alla conversione), costruttore `DbConnection(persistenceUnitName, jdbcUrl, jdbcUser, jdbcPassword)` — stesso corpo per i 13 metodi pubblici esistenti, cambia solo la dichiarazione di tipo/costruttore. `LinkageUnitConfig.getDbConnection()` la costruisce **lazy** (non nel loader): aprire una `EntityManagerFactory` con `hbm2ddl.auto=update` tocca subito la rete, quindi il solo caricamento/validazione della config JSON resta un test puro senza Postgres (`LinkageUnitConfigLoaderTest`). Mai più di un `DbConnection` vivo per processo.
  - **3 Postgres distinti** invece di 1 condiviso: `primat-linkage-unit/src/main/resources/META-INF/persistence.xml` è passato da 1 a 3 `<persistence-unit>` (`PrimatCenterClustering`/`PrimatMscdAp`/`PrimatMscdApNoClean`, stessa lista di 13 classi `@Entity`/`@Embeddable` ripetuta identica in ognuna, default DB `primat_center_clustering`/`primat_mscd_ap`/`primat_mscd_ap_no_clean` — sovrascritti a runtime dai valori di `database.*` della config JSON). Nessuna 4ª PU per MCL (resta non persistente). Chi aveva dati nel vecchio DB unico `primat`/PU `"Primat"` li ritrova orfani, nessuna migrazione automatica.
  - `MultiSourceLinkage.runMscdAp`/nuovo `runCenterClustering` e `PersistentLinkTableBuilder.build(...)` guadagnano un parametro esplicito `DbConnection` (non più letto dal singleton); `LinkStrategy` esteso a `{MSCD_AP, CENTER_CLUSTERING, MCL}` (solo etichetta di stampa, MSCD-AP-no-clean riusa il tag `MSCD_AP`).

- **Constant Weight Encoding + missing-value bucketing nella codifica RBF, salt FEBRL per-colonna (2026-09-22)** — due tecniche per mitigare il problema (scoperto analizzando come la pipeline gestisce un attributo QID vuoto) che un campo mancante produceva sempre lo stesso pattern di bit nell'RBF, indipendentemente dal record: correlazione strutturale sfruttabile e distorsione della similarità Dice/Jaccard a valle. Design deciso dopo aver scartato alternative più invasive (bitmask di presenza campi trasmesso alla LU, passaggio da RBF combinato ad Attribute-level Bloom Filter, filler derivato dagli altri attributi del record) perché introducevano nuova superficie di leak o accoppiamenti indesiderati tra campi — entrambe le tecniche restano interamente lato Data Owner, nessun cambio al formato RBF né nuovi metadati trasmessi.
  - **Constant Weight Encoding (CWE)**: nuova `ConstantWeightTrigramExtractor extends TrigramExtractor` (`primat-common/.../extraction/qgram/`, stesso pattern di `SpecialTrigramExtractor`) normalizza il numero di trigrammi unici estratti per un attributo dentro una banda configurabile `[minTrigrams, maxTrigrams]` (JSON per-colonna `columns[].constantWeightEncoding.{enabled,minTrigrams,maxTrigrams}`), senza forzare un valore esatto (variazione naturale dentro banda = nessun intervento). Sopra `maxTrigrams`: selezione via hash-ranking deterministico (`hash(trigramma+saltAttributo)` crescente, mai troncatura posizionale, che favorirebbe stringhe con prefisso comune). Sotto `minTrigrams` su valore non vuoto: filler `"CWE_FILL_" + hash(valore+salt+i)`, legato al contenuto reale (non un padding fisso condiviso). Un attributo vuoto non viene mai toccato da questa classe (delegato al punto sotto); `enabled=false`/assente è equivalente byte-per-byte al vecchio `TrigramExtractor`. `DataOwnerPipeline.buildRbfDefinition()` non condivide più un'unica istanza `TrigramExtractor` fra tutte le colonne (comportamento pre-esistente): ne costruisce una `ConstantWeightTrigramExtractor` per colonna, parametrizzata dai settaggi CWE di quella `ColumnConfig`.
